# 構成 ARCHITECTURE

## 全体像

```
[データソース apexdb.gg]
        ↑ 15分ごとに取得（サーバー側 cron）
[取得・保存レイヤー]
  - ページを取得し、モード別スロットをパース
  - ミックステープはサイクル対応表でモード種別を付与（DATA.md）
  - rotation_snapshots に最新1件を保存
        ↓ 保存済みデータを即返す（外部取得で待たせない）
[表示レイヤー（クライアント）]
  - スナップショットを受け取り即描画
  - 残り時間は end 時刻から毎秒ローカル計算
  - 手動「更新」ボタンでのみ再取得を要求
  - お気に入り★の登録・解除、ライブ中のお気に入り強調
```

## 設計上の判断と理由

1. **表示時に外部APIを直接叩かない**
   - 初回表示が外部の応答速度に依存すると、埋め込み表示やウィジェットのスナップショット撮影でタイムアウトしやすい
   - 「古くてもまず保存済みを即返し、更新は裏側（cron／手動）で行う」形が安定する
2. **カウントダウンはクライアント計算**
   - 終了時刻（絶対時刻）だけ渡せば、通信なしで毎秒表示を進められる
3. **取得失敗に強くする**
   - 取得エラーでも前回スナップショットを表示し続ける。画面をエラー状態にしない
4. **外部リソース依存を減らす**
   - Webフォント等の外部読み込みは表示の前提にしない

## Museスペース版の実装メモ

- ホスト：Muse のフルスタック・スペース（サーバーアクション＋定期リフレッシュ）
- アクション：`getRotation`（保存済みを即返却）／`refreshRotation`（取得して保存）／`toggleFavorite`
- 定期実行：15分間隔の cron が `refreshRotation` を呼ぶ

## 一般のWebアプリとして再実装する場合

- バックエンドは小さな定期ジョブ＋JSON保存で足りる（DBは最新スナップショット1件＋お気に入りだけ）
- フロントエンドは静的HTML+JSでも再現可能。その場合お気に入りは localStorage でよい
- APIキーが要る代替ソースを使う場合は、キーをサーバー側に置くこと
