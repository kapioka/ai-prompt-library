# データソースと取得方法 DATA

## 主データソース（APIキー不要）

- **apexdb.gg のマップローテーションページ**（ https://apexdb.gg/map-rotation/ ）
  - ページ内に、モード別のスロット情報が構造化データとして埋め込まれている
  - 各スロット：`map`（英語名）、`start` / `end`（Unix秒・UTC）、モードキー（`battle_royale` / `ranked` / `ltm` / `wildcard`）
  - 先のスロットには `projected: true`（繰り返しサイクルからの予測）が付く場合がある
  - データの出典は Apex Legends Status（apexlegendsstatus.com）とページ内に明記されている
- 取得間隔は15分。取得元の負荷に配慮し、それ以上頻繁に叩かない

## 代替データソース（APIキー必要）

- **Apex Legends Status API**（ https://apexlegendsapi.com/ ）
  - `GET https://api.mozambiquehe.re/maprotation?version=2&auth=<API_KEY>`
  - 無料キーを取得すれば、現在／次のマップをJSONで直接取得できる
  - キーはサーバー側でのみ使い、クライアントに露出させない

## ミックステープのモード種別（コントロール等）の導出

データソースのミックステープ（ltm）スロットは「マップ名＋時刻」しか持たず、モード種別（チームデスマッチ／コントロール／ガンゲーム）は含まれない。
シーズン中はプレイリストが固定サイクルで回るため、スロット開始時刻から導出できる。

### シーズン31 スプリット1 のサイクル（実データで照合済み）

スロットは15分刻み。`position = floor(start / 900) mod 9` とすると：

| position | モード | マップ |
|---|---|---|
| 0 | チームデスマッチ | Thunderdome（サンダードーム） |
| 1 | コントロール | Production Yard（生産工場） |
| 2 | ガンゲーム | Skull Town（スカルタウン） |
| 3 | チームデスマッチ | Fragment（フラグメント） |
| 4 | コントロール | Barometer（バロメーター） |
| 5 | ガンゲーム | Wattson Pylon（ワットソン・パイロン） |
| 6 | チームデスマッチ | Skull Town（スカルタウン） |
| 7 | コントロール | Thunderdome（サンダードーム） |
| 8 | ガンゲーム | Monument（モニュメント） |

モードのプール（EA公式パッチノート、シーズン31）：
- チームデスマッチ：Thunderdome / Fragment / Skull Town
- コントロール：Production Yard / Barometer / Thunderdome
- ガンゲーム：Skull Town / Wattson Pylon / Monument

### 安全策（必須）

- **実スロットのマップ名が対応表と一致するときだけモード名を表示する**。一致しない場合はマップ名のみ表示し、モードを推測で出さない
- シーズン／スプリットが変わってプールや順序が変わると、自動的にモード表示が消える側に倒れる
- イベント等で通常サイクルが崩れた場合も同様

## バトルロイヤルの先行スロットの予測補完

取得元はバトルロイヤルについて「現在＋次1件」しか返さないことがある。「3つ先まで」表示するため、シーズンの固定サイクルから後続を投影する。

- シーズン31のプール（EA公表）：Storm Point / E-District / Broken Moon、90分枠
- サイクル順：E-District → Broken Moon → Storm Point（取得元がランクで返すスロットの並びと、実測した遷移の一致で裏取りする）
- 投影したスロットには必ず「予測」と明示する
- 安全策：既知スロットの並びがサイクル順と一致しなくなったら投影を自動で止める。順序を推測で作らない

## ワイルドカードの扱い

- ワイルドカードはイベント性が強く、長期枠（数週間同じマップ等）になることがある
- 固定サイクルの裏取りが取れないため予測補完は行わない。既知スロットの後に「以降は未定」と明示する

## 注意

- ローテーションは EA の運営都合で予告なく変わることがある。最終的な正はゲーム内ロビー表示
- 取得元のサイト構成が変わるとパースが壊れる可能性があるため、取得失敗時は前回データを表示し続ける設計にする（`SPEC.md` 参照）
